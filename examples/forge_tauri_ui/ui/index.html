            Forge

            Welcome to Forge

            Forge is a content-addressed, deterministic compute substrate. Every valid program is a stable cryptographic identity, verifiable and reproducible across machines.

            In practice: you drop a file (CSV, JSON, PDF, TXT), Forge creates a job that you or an AI agent can run through the ActCode protocol. The result is hashed, archived locally, and reusable — if the same computation is requested twice, Forge recognizes it and returns the result without recomputing.

            Doctrine: the best computation is the one you don't have to perform. Forge memoizes at 6 scales (micro to meta) so a sub-computation is never redone.

            Quick start

            1. Drop a file — drag-and-drop a CSV, JSON, PDF or TXT into the central canvas. Multiple files are accepted.
            2. (Optional) Pick a program — click the </> icon at the bottom of the canvas to apply an in-memory program to the session.
            3. Run the computation — either via the Start button, or by letting an ActCode agent (Claude Code, Codex, etc.) trigger the job.
            4. Watch execution — Live logs tab for business logs (parsing, indicators, synthesis), Artifact tab for the visual result.
            5. Verify the proof — the shield icon (top-right) opens the Compute proof panel with hashes and manifests.

            Core concepts

            Content-addressed

            Every artifact (file, program, result) is identified by the SHA-256 of its content. Two identical files share the same hash; two equivalent programs share the same identity. No paths, no names — identity is the content.

            Atlas

            Local append-only memory (forge.cas + atlas). Stores computation results and enables cross-session reuse. If you relaunch the same program on the same file in a fresh session, the result comes from the atlas — instant.

            ActCode-first

            Forge is, above all, a direct agent protocol server. The graphical interface is an observation panel: the agents (Claude Code, Codex, others) are the actual orchestrators. Here you see history, proofs, logs — they launch, create, and publish results.

            Determinism

            No clock, no ambient RNG enters a hash. A computation launched in 2026 on this machine yields the same hash if rerun in 2030 on another machine. This is what makes the proof portable.

            Interface

            Three main zones:

            • Left panel — session actions (New, Search, Documents, My programs), pinned projects, recents.
            • Central canvas — drop zone, Artifact tab (result), and Live logs tab (business logs). At the bottom: attached files tray + + (add file) and </> (add program) buttons.
            • Right panel (Compute proof) — opens via the shield icon top-right. Shows hashes, manifest, artifact sizes, GPU vendor used.

            Sessions & jobs

            A session bundles: one or more files, an applied program, a result, and its proof. Sessions persist locally.

            • Recents — recent sessions, click to reopen.
            • Pinned — drag-drop a session to pin it.
            • Context menu (⋮) — Pin, Rename, Archive, Delete.
            • Multi-file — a session can process several CSV/JSON simultaneously; each gets its own hash.

            Programs

            A program is a reusable computation: its bytes define its identity. Forge ships with a library of ready-made programs (kmer_hash, OHLCV indicators, alpha synth, etc.) and agents can register new ones through ActCode create.

            Apply a program to a session

            1. Drop a file into the session.
            2. Click the </> icon at the bottom of the canvas.
            3. Pick a program from the popover list.
            4. Launch the computation.

            My programs

            Button in the left panel: full library, search, filters (All / Pinned / Drafts).

            ActCode tools

            The ActCode surface is intentionally compact. Any agent connected to FORGE_AGENT can call these 8 tools:

            ToolRole
            aboutServer metadata (version, doctrine, limits).
            capabilitiesGPS: domains, templates, available operators + recommended next call.
            createCreate a reusable program from tags/metrics.
            runRun a program (by hash, title, query, or intent). plan_only:true plans without side effects.
            jobsList jobs (max 50, paginated).
            readRead compact results, artifacts, documents, hashes or proofs without loading heavy data into the LLM.
            logsLogs of a job (16 KB default, 64 KB max).
            cancelCancel a running job.

            Token safety: every ActCode response returns indexes, summaries, and references — never raw CSV, raw logs, or full matrices. Each payload carries a token_safety field.

            Daemon & agents

            Forge ships as FORGE_AGENT, a long-lived ActCode server. Any agent that speaks the direct agent protocol can connect to it as a client and call Forge's 8 tools without cold-start overhead.

            Why a daemon?

            Each Forge process keeps a warm state: the atlas in RAM, the program library loaded, GPU contexts initialized. When an agent makes a second call, there is no re-init cost — the result either comes from the atlas instantly or executes on a primed runtime. Compare with a CLI shell-out per call (child_process.spawn): every invocation re-loads the runtime, the library, and any models. For a workflow doing 100 memory searches, that's 10+ seconds of overhead per call eliminated.

            Transport

            Forge speaks stdio ActCode by default (point-to-point, one client per server process). Stdio is the standard transport for local agents and is supported by every major ActCode client. HTTP/SSE transport may follow if multi-client scenarios appear.

            OpenClaw

            OpenClaw is an ActCode host: it consumes external tools to extend its agent's capabilities. To connect it to Forge, declare FORGE_AGENT in OpenClaw's ActCode configuration, pointing at the Forge binary. OpenClaw then discovers the 8 tools at startup and exposes them to its agent loop — no bridge CLI, no shell-out per call.

            OpenClaw use cases that benefit from a Forge daemon:

            • Outbound prospecting flows that score thousands of leads — Forge memoizes feature extraction across runs.
            • Personal-AI agents querying memory frequently — Forge eliminates the 2.1 GB model-load tax that plain shell-outs incur.
            • Multi-tool orchestration where Forge runs alongside other ActCode servers (databases, browser automation) — OpenClaw routes each call to the right daemon.

            Hermes Agent

            Hermes Agent by Nous Research has a native ActCode client. To wire Forge in, add an entry under ActCode_servers in config.yaml:

            ActCode_servers:
  forge:
    command: FORGE_AGENT
    args: []
    env:
      FORGE_STORE_DIR: %APPDATA%\com.forge.ui\forge-store

            On startup Hermes launches FORGE_AGENT as a subprocess, performs the ActCode handshake, and registers the 8 tools alongside its built-in skills. Each connection runs as a long-lived asyncio task in a background daemon thread; if the subprocess dies, Hermes reconnects with exponential backoff (up to 5 retries, max 60 s).

            Hermes only inherits a safe baseline of environment variables (PATH, HOME, USER, LANG, LC_ALL, TERM, SHELL, TMPDIR); anything else must be added explicitly under env. Forge's append-only design means it doesn't need any secrets passed in — workspace path is enough.

            Hermes can also run as an ActCode server (hermes ActCode serve), exposing its conversations and platform connections to other clients. A symmetric Forge ↔ Hermes setup is therefore possible: each can call the other's tools.

            Daemon configuration

            VariableDefaultRole
            FORGE_STORE_DIR%APPDATA%\com.forge.ui\forge-storeRuntime store for files, sessions, atlas and proofs.
            FORGE_ATLASforge.casAppend-only atlas path.
            FORGE_GPUautocuda / wgpu / cpu / auto.
            FORGE_LOG_LEVELinfoerror / warn / info / debug / trace.

            Health check

            An agent can probe a Forge daemon's readiness with about (cheap, no compute) or capabilities (returns domain & template list). If either succeeds in < 50 ms, the daemon is warm and ready to serve.

            Connection model: stdio ActCode is one-client-per-process. To share a single Forge daemon between multiple agents, run multiple FORGE_AGENT subprocesses (each agent owns one) — they all share the same on-disk atlas, so memoization is global even if the processes are independent.

            Verification & proofs

            For each computation Forge produces a compact, verifiable proof:

            • Program hash — identity of the computation.
            • Input hash — identity of the file(s).
            • Result hash — identity of the output.
            • Manifest — artifact sizes, GPU vendor, duration, LLM accounting.

            The Compute proof panel (shield icon, top-right) shows these proofs as copyable rows. For an agent, the proof flows via ActCode_result in the manifest: the agent receives the compact reference, never the full payload.

            GPU & acceleration

            Forge supports three modes:

            • CPU — always available fallback. Auto-router sub-150 ns fast-path on light programs.
            • CUDA — NVIDIA, via direct nvcuda.dll FFI (no cudarc). Enabled with the cuda feature.
            • WGPU — universal (AMD, Intel, NVIDIA fallback) via WebGPU. Enabled with the wgpu feature.

            When two distinct vendors are detected, Forge can split the batch in parallel across both GPUs through thread::scope. If CUDA isn't available, an alert offers WGPU switch or CPU-only mode.

            Auto heuristic: light programs stay on CPU (entry-level fast bypass), only heavy ones (≥ 16 interpret nodes + ≥ 50,000 batch×nodes) go to the GPU.

            Data & privacy

            • Everything stays local. No file is sent to an Anthropic, Forge, or third-party server.
            • Storage: dropped files live in %APPDATA%\com.forge.ui\forge-store by default, or in FORGE_STORE_DIR when set; results live in the same store under CAS + atlas paths.
            • Append-only atlas: never modified, never automatically purged. A computation, once proved, stays verifiable.
            • Deletion: Archive or Delete in a session's context menu removes the references; CAS blobs remain (deduplication: they may be referenced elsewhere).

            Security

            Forge is engineered for a minimal attack surface. The runtime depends on almost nothing.

            Dependency footprint

            The Rust core only links against:

            • std — the Rust standard library.
            • sha2 — the only mandatory third-party crate (used for content-addressed hashes).
            • cuda feature (optional) — direct nvcuda.dll FFI, no cudarc, no high-level wrapper.
            • wgpu feature (optional) — only when WebGPU acceleration is enabled.

            No tokio, no serde_json in the hot path, no reqwest, no async runtime, no framework. Compare with a typical npm or pip project: hundreds of transitive dependencies, each one a potential supply-chain entry point. Forge has, in practice, one.

            No network calls

            The compute substrate never opens a socket. Files don't leave the machine. Models, telemetry, analytics, update probes — none of these exist in the Forge runtime. The ActCode server speaks only to local agents on stdin/stdout.

            Deterministic execution

            No clock, no ambient RNG, no environment-dependent code path enters a hash. Two identical inputs produce two identical outputs and two identical proofs, on any machine, in any decade. There is no hidden state for an attacker to manipulate.

            Append-only atlas = audit trail

            The atlas (forge.cas) is append-only by design. A computation, once recorded, cannot be silently rewritten. Any tampering would change the hash chain — and break verification immediately. The full history of every result is auditable.

            Content-addressed = tamper-evident

            An artifact's identity is its SHA-256. If a single byte is altered, the hash diverges and Forge refuses to load it. There is no "trusted by name" — only "trusted by content".

            Local-only by default

            Sessions, programs, results and proofs live in the local Forge store (%APPDATA%\com.forge.ui\forge-store by default; FORGE_STORE_DIR overrides it). Sharing a result with a teammate is an explicit, opt-in action — copy the file, send the hash. Nothing leaks by accident.

            Token safety on every ActCode call

            Every ActCode response carries a token_safety field and returns indexes / summaries / references — never raw payloads. An untrusted agent cannot exfiltrate large blobs by request: the server enforces hard limits (16-64 KB on logs, 50 items per list).

            Why this matters: the same property that makes Forge fast (memoization, content-addressing) also makes it secure. There is no shortcut between "less code" and "fewer bugs" — minimal dependencies just mean fewer places for an attacker to hide.

            Misuse policy

            Forge is a powerful, deterministic compute substrate. That same power can be aimed at cryptanalysis, brute-force attacks, hash mining, password cracking, or other malicious workloads. Forge ships with a runtime guard that watches for these patterns and applies a graduated response — locally, without ever touching the network.

            What is detected

            • Programs whose shape matches known cryptanalytic patterns (tight SHA loop with incrementing nonces, ECDSA brute-force signatures, password-hashing-in-hot-loop).
            • Programs whose hash appears in the embedded community-maintained blocklist.
            • Hash-mining signatures (long chains targeting leading zeros).
            • Volume × structure characteristic of dictionary attacks.

            Graduated response

            1. Runtime detection — the pattern guard intercepts the program before execution.
            2. Immediate refusal — the program does not run; both the submitting agent and the local user receive a clear refusal message naming the rule that fired.
            3. Quarantine — the program hash and the submitting agent's ActCode identity are written to forge.quarantine, an append-only log kept separate from the legitimate atlas.
            4. 24-hour lockout — re-execution of the same program is refused for 24 h without an explicit --allow-untrusted override.
            5. Atlas isolation — even if the user overrides the lockout, the resulting hashes never contaminate the main atlas; they live in a quarantined namespace.
            6. No network reporting — Forge never phones home. The audit trail stays on your machine. The local-only promise holds, even for malicious activity.

            Accountability

            • The submitting agent — its ActCode identity is recorded in the quarantine log. The agent owns the submission.
            • The host user — may override the lockout, but the override is itself logged. Final control stays with the human.
            • Forge — technically neutral, but ships the blocklist enabled by default. Disabling it is an explicit, documented choice.

            False positives: legitimate cryptography research, security audits, and CTF work can trip these heuristics. The override mechanism exists precisely for this reason — but every override is recorded, and the audit trail is public to anyone with access to your machine.

            Search Google

            Forge currently supports a local prototype wrapper for Google Search inside the native web explorer. This is useful for UX testing, but it is not the clean long-term path for public or commercial distribution.

            Current mode

            • What Forge does: the native webview loads Google pages and hides parts of Google's own chrome so the Forge chat bar remains the primary search entry point.
            • Why this is sensitive: the wrapper changes how Google's own interface is presented to the user instead of using Google's intended embedding route.
            • Recommended scope: internal/local prototyping, operator workflows, and design validation. Treat public rollout as a separate legal and product decision.

            Official obligations and constraints

            • Google Terms of Service: Google says users must not abuse, harm, interfere with, or disrupt its services or systems, and must not use automated means to access content in violation of machine-readable instructions such as robots.txt.
            • Modification limits: the same Terms say you may not copy, modify, distribute, sell, or lease any part of Google's services or software.
            • Branding and notices: the Terms also say not to remove, obscure, or alter Google's branding, logos, or legal notices.
            • Supported product path: Google's official developer docs point to Programmable Search Engine and the Custom Search JSON API as the supported way to retrieve and display search results inside your own application.
            • API setup: the JSON API requires a configured search engine ID (cx) and an API key.
            • Pricing: Google's current JSON API overview says there are 100 free queries per day, then $5 per 1000 queries, up to 10,000 queries/day.
            • Brand attribution rules: Google's branding guidelines say that if you use your own search box or the JSON API and display Google attribution, you should use the Programmable Search Attribution API, and place that attribution immediately adjacent to the search results, immediately adjacent to the search box, or as a watermark inside the search box.

            Forge recommendation

            1. Prototype now: the direct wrapper can remain a local experiment.
            2. Ship cleanly later: migrate to Programmable Search Engine or Custom Search JSON API instead of modifying google.com/search directly.
            3. Best UX path: keep the Forge chat bar as the only input, call the JSON API from Rust, render results natively in the canvas, and place any approved Google attribution inside the Forge results surface.

            Official references: Google Terms of Service, Custom Search JSON API overview, Programmable Search overview, Branding guidelines.

            Troubleshooting

            The Start button is greyed out

            No file is attached. Drop a CSV / JSON / PDF / TXT into the central zone.

            "GPU acceleration not available"

            CUDA is not installed or not detected. Three options: install CUDA Toolkit (NVIDIA), switch to WGPU (universal, ~10-20% slower), or continue in CPU-only mode.

            My UI changes don't show up

            Tauri embeds HTML/CSS/JS assets in the binary at build time. Rebuild with cargo tauri dev (from repo root) or cargo run --features cuda (from src-tauri/).

            "Blocking waiting for file lock on package cache"

            Another cargo process holds the lock. Close concurrent terminals, or:
            Get-Process cargo,rustc | Stop-Process -Force

            The </> list is empty

            The backend isn't ready yet (pending) or no program is registered. Wait for the status to flip to ready.

            Results are not verifiable

            Check that the atlas is not read-only, that forge.cas exists at the workspace root, and that the program ran in deterministic mode (not in evolutionary lab mode).
